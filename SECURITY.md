# Security

## Reporting a problem

Use **Report a vulnerability** on this repository's Security tab (GitHub private vulnerability reporting), with a description of the problem and how to reproduce it. Please do not open a public issue for a security problem. We aim to reply within five working days.

Report abuse of the feedback intake the same way, such as a flood of fake reports or a leaked app key.

## What this repository handles

- **App keys** identify an app to the intake. They ship inside apps, so treat them as public identifiers that can be revoked, not as secrets. Each key has its own daily limit, with owner submissions counted apart from other feedback, and may be limited to feedback or to owner submissions with `kinds` (see [docs/self-hosting.md](docs/self-hosting.md)). To revoke one, set the `APP_KEYS` secret again without it: setting a secret deploys it at once.
- **Device ids** are random per-install UUIDs. The intake stores only the first 16 hex characters of SHA-256 over a secret salt and the id. Raw device ids are never stored, and hashes are never written to the public `data` repository or a PR body.
- **Client networks.** The intake reads the client address from `CF-Connecting-IP`, cuts it to its IPv4 /24 or IPv6 /48 and stores only the same kind of salted hash, never the address. It limits submissions per network a day, and the apply rules count distinct networks, so new device ids from one client do not count as more people.
- **Free text** (report notes and review text) has email addresses, phone numbers and links replaced with `[removed]` by the intake. The apply step refuses reviews that still contain contact details, links, social media handles, personal names or offensive language, and withholds such notes from PR bodies. Any other traveller value a PR body quotes (a name, a description, a fact value, a Commons file name) is withheld when it fails the text rules, and markdown punctuation in what is kept is escaped, so traveller text never makes a link. A name or description report that fails the text rules goes to a person as a note, and its value is not written to the review branch.
- **Contributors.** An app sends an opaque per-account id with reviews and review reports, never a name or email. The intake stores and publishes only `ctr_` and the first 16 hex characters of SHA-256 over the salt, the app name and that id, so a published id cannot be traced to an account and differs between apps. An App Attest key id is kept the same way (`ak_`). Each contributor and each attested key has a daily limit. A photo removal or erasure is accepted for the contributor value alone unless the app key has `contributor_proof_key`; then it needs a short-lived Ed25519 proof the app's own server signed for that contributor, action and photo, and without one nothing is withheld or stored. A review may carry the same kind of proof (`contributor_proof`, action `review`). With `contributor_proof_key` the intake checks it and marks the stored item `proved`. A review is never refused for lacking one: a review that replaces the same contributor's earlier review of a place is published by the apply step only when it was `proved` or comes from the same device or attested key as the review it replaces, and otherwise goes to a person.
- **Reviews.** One review per contributor per place, the newer replacing the older. A contributor's first review, and text sent word for word for another place, go to a person. The apply step checks review text with the SDK's text rules (`textProblem`), as it does every other piece of free text, and also refuses advertising (prices, calls to book, discounts) and offensive words spelled with spaces, look-alike characters, masks or repeated letters.
- **Erasure.** A contributor's `review_erasure` removes every review line they wrote, on every place, at the next apply run, and their held reviews from the review branch. It names only the contributor, so with `contributor_proof_key` on the app key the intake takes it only with a proof the app's server signed for that contributor and the `review_erasure` action. A proof for a photo action is not accepted for reviews, nor the other way round.
- **Reports and blocking.** Every review report goes to a person on the `feedback/review` PR, who looks at reported reviews within 24 hours. Reports from three different contributors, on three different client networks, hide a review until the person decides. A person hides a review or blocks a contributor with `python -m pipeline.moderate` in `data`. Everything a blocked contributor sends is refused, except a request to remove or erase their own photos, and their reviews are left out of the release and the rating. Hateful content or personal details are hidden by the third report or at once by a person.
- **Attestation.** An app key with `requires_attestation` accepts feedback only with an Apple App Attest assertion or a Google Play Integrity token over the exact body. For App Attest the intake checks the attestation once per install as Apple describes (certificate chain to Apple's App Attest root, nonce from a one-time server challenge, key id, app id, counter 0, environment and the app's launch validation category: TestFlight or App Store in production), keeps the public key and then checks every assertion's signature, app id and rising counter. Submissions queue offline, so assertions carry no server challenge; the rising counter stops replays. Registered keys and counters live in Workers KV, which is eventually consistent, so an assertion replayed within about a minute at another Cloudflare location could pass once; the apply step's one-review-per-contributor rule and the daily limits bound what that gains. For Play Integrity the intake decodes the token with Google as a service account limited to the `playintegrity` scope and requires the request hash, the package, a token under 5 minutes old, `PLAY_RECOGNIZED` and `MEETS_DEVICE_INTEGRITY`.
- **Secrets** (`APP_KEYS`, `DEVICE_SALT`, `PLACES_TOKEN`, `URLHAUS_KEY`, `GOOGLE_SERVICE_ACCOUNT`, the photo service's `PHOTO_PASS_SECRET`, `PHOTO_KEYS`, `PHOTO_OPERATOR_TOKEN` and `REVIEW_PREVIEW_SECRET`, and the GitHub App keys) live in Cloudflare Worker secrets and GitHub Actions secrets. None are in this repository, and the `wrangler.toml` files hold placeholders only. `PLACES_TOKEN` guards the intake's operator routes (the recent list, progress, the place index and the queue health check), and the intake compares it by hash.

## Owners

- **Tokens.** A claim or listing returns a 32 byte random token once. The intake stores only its SHA-256, in the claim and in `owners/<place id>.json` once approved, and replaces an update's token with its hash before storage. Nothing logs the token.
- **Contact details.** Owner names and emails stay in the private inbox (`owner-claims/`, `owners/` and the stored submissions). They are never written to `data` or a PR.
- **Approval.** A claim reaches `data` only after a person ticks its box in the `feedback/review` PR and merges it. Boxes count only in review PRs the bot opened in the `data` repository itself, never in a PR from a fork, and only in the PR body and in comments written by the bot, at the start of a line, so text from an owner cannot add or tick one.
- **Proof pages.** The apply run fetches an owner's proof page with https only, on public host names, checking every resolved address before connecting (no loopback, private, link-local or shared ranges), following at most three redirects that are each checked again, with a 10 second timeout and a 1 MB cap. Each run spends at most 3 minutes on proof pages, 4 at a time and oldest first, and claims it did not reach wait for the next run.

## GitHub App permissions

- `opencampingdb-intake` is used by the intake. It has `contents: write` on `inbox`, plus `actions: write` on `inbox` when the intake starts the apply workflow, and `contents: write` and `pull_requests: write` on `data` when the AI reviewer is on. Its private key lives only in the Worker's secrets. Each token it requests is limited to one repository and the permissions that call needs.
- `opencampingdb-bot` is used by the apply workflow. It has `contents: write` on `inbox`, and `contents: write` plus `pull_requests: write` on `data`, plus `actions: write` on `data` when the workflow starts the data release. Its private key lives only in the inbox repository's Actions secrets, never in the Worker. Each token the workflow requests is limited to one repository.
- A leaked intake key can add files to `inbox`. With the AI reviewer on it also has write access to `data`, so protect `main` there: the reviewer itself writes only to `feedback/review`, which a person merges. A leaked bot key cannot be used from the Worker, and its PRs to `data` still pass through CI and, for anything outside the automatic rules, a person.

## Workflows

Every third-party action is pinned to a full commit SHA. Workflows default to `contents: read`, and no untrusted value is expanded inside a `run:` script; values reach scripts through environment variables.
